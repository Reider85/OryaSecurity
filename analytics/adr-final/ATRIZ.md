## 0. TL;DR

Классическая архитектура из ARCHITECT.md решает проблемы «в лоб»: добавляет компоненты (Vault, OPA, Qdrant, ML-классификатор), каждое решение порождает новые противоречия. ТРИЗ предлагает идти от **ИКР** — идеального конечного результата — и разрешать противоречия через **40 приёмов**, а не компромиссы.

В этом документе:
1. Сформулирован **ИКР-1 и ИКР-2** для сканера (раздел 2).
2. Выявлено **12 технических противоречий** и **3 физических** (раздел 3).
3. Применены **17 из 40 приёмов** ТРИЗ к конкретным узлам архитектуры (раздел 4).
4. Сформулированы **5 законов развития**, применимых к эволюции сканера (раздел 5).
5. Проведён **вепольный анализ** для трёх критических подсистем (раздел 6).
6. Результаты зафиксированы в **10 новых ADR (0016–0025)** (раздел 7).

**Главный сдвиг парадигмы:** сканер должен **исчезнуть** как отдельный компонент и стать **свойством самой LLM-инфраструктуры** (ИКР — системы нет, функция выполняется).

## 1. Введение в ТРИЗ-подход

### 1.1. Почему ТРИЗ применима к архитектуре ПО

ТРИЗ разработана для инженерных систем, но архитектура ПО — тоже инженерия. ТРИЗ работает там, где есть:
- **Технические противоречия** — улучшение одного параметра ухудшает другой (latency ↑ → безопасность ↑).
- **Физические противоречия** — к одному элементу предъявляются взаимоисключающие требования (должен быть inline для защиты, должен быть async для UX).
- **Неочевидные ресурсы** — мы часто не видим свободных ресурсов вокруг проблемы.

Классический подход «компромисс» в архитектуре — это trade-off matrix, где выбирают «меньшее зло». ТРИЗ целенаправленно ищет **разрешение противоречия** (выход за рамки компромисса).

### 1.2. Ключевые инструменты ТРИЗ, применённые в документе

| Инструмент | Что делает | Раздел |
|---|---|---|
| **ИКР** (Идеальный конечный результат) | Система выполняет функцию, а самой системы нет | 2 |
| **Технические противоречия** | Формулировка «если A, то B ухудшается» + применение 40 приёмов | 3.1, 4 |
| **Физические противоречия** | К одному элементу — взаимоисключающие требования | 3.2, 4 |
| **40 приёмов** | Каталог проверенных паттернов разрешения | 4 |
| **Законы развития техсистем** | Прогноз эволюции архитектуры | 5 |
| **Вепольный анализ** | Модель «вещество-поле» для структурного анализа | 6 |
| **Ресурсный анализ** | Поиск скрытых бесплатных ресурсов | 7 |
| **Маленькие люди** | Модель поведения объектов через антропоморфные агенты | 8 |

## 2. ИКР — Идеальный конечный результат

### 2.1. ИКР-1 (функциональный)

> **Сканер отсутствует как отдельный компонент, а функция безопасности выполняется самой LLM-инфраструктурой.**

Формально:
- Пользователь отправляет промпт — LLM получает уже безопасный промпт.
- LLM генерирует ответ — пользователь получает уже безопасный ответ.
- Никакого «между ними» — нет прокси, нет sidecar, нет SDK.
- Безопасность — **свойство** взаимодействия, а не отдельного слоя.

**Что это значит на практике:**
- Безопасность baked-in в токенизатор LLM (на уровне обучения).
- LLM сама «знает» что нельзя выводить PII (через RLHF на safety corpus).
- Инфраструктура LLM-провайдера сама предоставляет hooks для политик клиента.

### 2.2. ИКР-2 (ресурсный)

> **Сканер использует только уже существующие в системе ресурсы, не добавляя новых компонентов.**

Ресурсы, которые уже есть в AI-приложении:
- LLM-провайдер (мощный семантический движок — можно использовать как детектор).
- Токенизатор LLM (уже считает embeddings).
- KV-cache LLM (уже содержит semantic-представление промпта).
- Логи LLM-провайдера (если есть доступ).
- Клиентский промпт (в нём самом — метаданные, структура, контекст).
- Время ожидания LLM (пока LLM генерирует — можно проверять предыдущий промпт).

**ИКР-2 для сканера:** использовать LLM-провайдера как детектор (LLM-as-judge), не поднимая отдельной ML-инфраструктуры.

### 2.3. ИКР для под-задач

| Под-задача | ИКР |
|---|---|
| Decision Cache | Кеша нет, но решение всегда мгновенное (результат предвычислен для всех возможных промптов) |
| Vector DB | Векторов нет, но похожесть определяется (через hash-семейство или learned index) |
| ML Classifier | Модели нет, но классификация делается (через токенизатор LLM + lightweight probe) |
| Audit log | Записи нет, но событие восстанавливается (через replay LLM-провайдера) |
| Redaction | Замены нет, но PII не уходит (LLM сама не выводит — через RLHF) |

### 2.4. Степень приближения к ИКР (текущая vs улучшенная)

| Параметр | Текущая архитектура | ИКР | Улучшенная (после ТРИЗ) |
|---|---|---|---|
| Кол-во компонентов | 14+ | 0 | 8 (минус 6 через fusion) |
| Inline задержка | p99 < 50 ms | 0 ms | p99 < 20 ms |
| Стоимость GPU | 1× T4 | 0 | 0.5× T4 (shared с LLM) |
| Зависимости | Vault, Qdrant, OPA, ML model | none | LLM-провайдер + cache |

## 4. Применение 40 приёмов ТРИЗ

Ниже — выборка **17 приёмов**, применимых к архитектуре сканера. Для каждого: формулировка → применение → результат.

### 4.1. Приём 1 — Дробление

> Разделить объект на независимые части.

**Применение к TC-1 (Sec↔Latency):**
Дробим pipeline не на «fast/slow path», а на **N асинхронных детекторов**, каждый из которых специализируется на одном классе угроз и работает независимо.

```
Промпт ─┬─> Detector A (prompt injection)  ─┐
        ├─> Detector B (PII)               ─┤
        ├─> Detector C (secrets)            ─┤─> PDP
        ├─> Detector D (toxicity)           ─┤
        └─> Detector E (topic policy)       ─┘
              async, cancel on first BLOCK
```

PDP ждёт не всех, а **до первого BLOCK** или до timeout — early-exit. Это даёт:
- Латентность = `min(N детекторов)`, а не `max` или `sum`.
- Блокирующий детектор (regex для PII) решает за <1ms, не дожидаясь ML.

**Результат:** новый компонент **Detector Fan-out с early-exit** (ADR-0016).

### 4.2. Приём 2 — Вынесение

> Вынести отдельную часть объекта или среды.

**Применение к PC-1 (Inline ↔ Async):**
Вынести «решающую» часть сканера в offline: pretrained политики, ML-модели, векторные индексы. Inline остаётся только lightweight comparator (hashed verdicts).

```
[Offline/precomputed]
- Prompt corpus → embeddings
- Policy evaluation results → hashed decision table
- ML inference → cached as Bloom filter

[Inline]
- Bloom filter lookup (O(1), <100µs)
- No ML, no vector DB
```

Это пример **precomputation pattern**: всё тяжёлое делается заранее, inline — только lookup.

**Результат:** **Precomputed Verdict Cache на Bloom filter** (ADR-0017).

### 4.3. Приём 3 — Местное качество

> Перейти от однородной структуры к неоднородной; каждая часть должна работать в оптимальных условиях.

**Применение к TC-5 (Multi-tenancy ↔ Cost):**
Не одинаковая изоляция для всех tenant'ов, а **tiered isolation**:
- Tier 1 (SMB): shared everything, payload filter.
- Tier 2 (Enterprise): per-tenant Vector DB namespace, shared scanner.
- Tier 3 (Regulated): per-tenant scanner pods, separate KMS, dedicated Vault.
- Tier 4 (Air-gapped): full silo, dedicated cluster.

Каждый tenant платит за нужный ему уровень изоляции.

**Результат:** **Tiered Multi-tenancy** (ADR-0018).

### 4.4. Приём 5 — Объединение

> Объединить однородные или смежные объекты; выполнить однородные операции одновременно.

**Применение к TC-11 (ML ↔ CPU cost):**
Объединить ML-классификатор и embedding service в **один shared model**: multilingual-e5 даёт embeddings И может быть fine-tuned для классификации (плюс linear head).

```
[Было]
prompt ─> [Embedding model] ─> vector ─> [Vector DB]
                                      └> [ML Classifier] ─> class
              2 GPU calls, 2 models

[Стало]
prompt ─> [Shared model: e5 + classification head] ─> {embedding, class}
              1 GPU call, 1 model
```

**Результат:** **Unified Embedding+Classifier Model** (ADR-0019).

### 4.5. Приём 6 — Универсальность

> Объект выполняет несколько функций, не требуя специальных частей.

**Применение к сканеру:**
LLM-as-judge — использовать саму LLM-провайдера как детектор (для сложных случаев). LLM уже есть в системе, дополнительного GPU не требуется.

- Fast path: rule + small ML.
- Slow path: vector search + LLM-as-judge (только для high-risk low-confidence).

Раньше LLM-as-judge rejected из-за latency (500–2000ms). Но если применять только к high-risk low-confidence (< 1% трафика) — acceptable.

**Результат:** **LLM-as-judge в fallback-режиме** (ADR-0020).

### 4.6. Приём 9 — Предварительное антидействие

> Заранее выполнить действие, противоположное нежелательному.

**Применение к TC-8 (Cache ↔ Staleness):**
Проблема: cache возвращает устаревший verdict после threat-intel update.
Anti-action: при загрузке нового threat-intel **предвычислить** новые verdicts для всех cache entries (batch, offline), и атомарно swap cache.

```
1. Threat-intel update arrives
2. Pull all cached prompts (10K)
3. Re-evaluate each in batch (offline, 5 минут)
4. Atomic swap cache (zero-downtime)
```

Cache hit rate остаётся высоким, staleness = 0.

**Результат:** **Predictive Cache Invalidation** (ADR-0021).

### 4.7. Приём 10 — Предварительное действие

> Заранее выполнить нужное действие полностью или частично.

**Применение к streaming (TC-9):**
Пока LLM генерирует токены (3–15 сек), сканер **предварительно** проверяет следующий чанк в параллельном потоке.

```
LLM streaming:   [chunk1]──[chunk2]──[chunk3]──[chunk4]──> DONE
                          │          │          │
Parallel scan:           scan(c1)  scan(c2)  scan(c3)
                          │          │          │
                          └──as inspect──>──>──>──>──>──>┐
                                                              │
User receives: <──[c1, OK]──[c2, OK]──[c3, BLOCK]──────────┘
```

Сканер **на 1 чанк впереди** LLM-стрима — почти нулевая задержка инспекции.

**Результат:** **Predictive Streaming Inspector** (ADR-0022).

### 4.8. Приём 11 — Принцип «заранее подложенной подушки»

> Заранее заготовить аварийные средства.

**Применение к TC-7 (Audit ↔ Storage):**
Pre-allocate **rolling audit windows**: 
- Last 30 days — hot, queryable.
- 30–365 days — cold, compressed.
- 1–7 years — archive, hashchain-verified snapshots only.

Storage cost падает 10× (горячий аудит только 30 дней).

**Результат:** **Tiered Audit Storage** (часть ADR-0006 expansion).

### 4.9. Приём 13 — Наоборот (инверсия)

> Сделать наоборот — перевернуть объект вверх ногами, вывернуть наизнанку.

**Применение к PC-2 (PII visible ↔ masked):**
Вместо «маскировать PII до LLM» — **научить LLM не выводить PII** (RLHF на safety corpus). PII виден LLM (она может семантически работать с ним), но LLM обучена не выводить его обратно.

- Пользователь: «переведи мой SSN 123-45-6789»
- LLM видит SSN, работает с ним.
- LLM отвечает: «SSN не переводится, это US identifier» — не выводит само число.

Это **инверсия**: не сканер маскирует, а LLM соблюдает. Сканер только верифицирует post-factum (sampling).

**Результат:** **LLM-Native PII Restraint (RLHF-based)** (ADR-0023).

### 4.10. Приём 15 — Динамичность

> Характеристики объекта должны меняться так, чтобы быть оптимальными на каждом этапе работы.

**Применение к TC-12 (Policy ↔ Latency):**
Не статическая политика, а **adaptive policy complexity** в зависимости от контекста:
- Доверенный пользователь (history clean) → простая политика (1ms).
- Новый пользователь → средняя политика (5ms).
- Подозрительный контекст → сложная политика с LLM-as-judge (50ms).

```
user_trust_score = f(history, tenant, role)
policy_complexity = trust_score ? simple : complex
```

**Результат:** **Adaptive Policy Complexity** (ADR-0024).

### 4.11. Приём 17 — Переход в другое измерение

> Перейти от движения/расположения в одном слое к многомерному.

**Применение к vector search:**
Вместо одного векторного пространства — **multi-modal embedding space**:
- Semantic axis (multilingual-e5).
- Structural axis (prompt template fingerprint).
- Behavioral axis (user intent classifier).

Похожесть = комбинированная метрика по всем осям. Ловит атаки, которые похожи семантически, но различны структурно.

**Результат:** **Multi-modal Embedding Space** (часть ADR-0010 expansion).

### 4.12. Приём 19 — Переход в периодическое действие

> Перейти от непрерывного к периодическому/импульсному действию.

**Применение к ML inference:**
Вместо inference per request — **batched periodic inference**:
- Собираем промпты в буфер 5 ms.
- Один раз inference для batch=32.
- Разворачиваем вердикты обратно.

GPU utilization ↑ с 30% до 95%, latency avg ↑ на 5 ms, но p99 ↓ (стабильнее).

**Результат:** уже заложено в ADR-0009 (Batching), расширен через ADR-0019.

### 4.13. Приём 22 — Принцип «поворота вреда в пользу»

> Использовать вредный фактор для получения положительного эффекта.

**Применение к adversarial prompts:**
Атакующий присылает jailbreak → используем его как **новый training sample** (после проверки, что он не дубликат). Каждая атака делает систему сильнее.

```
1. Prompt blocked with high confidence
2. Auto-route to threat-intel corpus
3. After SecOps verification → added to training corpus
4. Next retrain: classifier learns this attack
```

Атакующий фактически бесплатно улучшает детектор.

**Результат:** **Adversarial Reinforcement Loop** (ADR-0025).

### 4.14. Приём 24 — Применение посредника

> Использовать промежуточный объект, переносящий/передающий действие.

**Применение к PC-3 (Cache global ↔ per-tenant):**
Глобальный cache с **proxy verifier**: cache lookup возвращает candidate verdict, который дополнительно верифицируется lightweight tenant-specific filter (Bloom filter per tenant).

```
[prompt hash] ─> global cache ─> candidate verdict
                                    │
                                    └─> tenant bloom filter (per-tenant)
                                          │
                                          └─> final verdict (or fall to slow path)
```

Глобальный cache (high hit rate) + per-tenant filter (изоляция) — без компромисса.

**Результат:** **Cache Proxy with Per-tenant Filter** (ADR-0026).

### 4.15. Приём 25 — Самообслуживание

> Объект должен сам себя обслуживать, выполняя вспомогательные операции.

**Применение к сканеру (overall):**
**Self-healing scanner** — компоненты сами детектят проблемы:
- Vector DB — пересобирает index при ухудшении recall.
- ML classifier — триггерит retrain при росте FP.
- Audit store — verifies hashchain integrity periodically.
- Cache — самоочищается при истечении TTL.

Без оператора — система устойчива.

**Результат:** **Self-healing Scanner** (ADR-0027).

### 4.16. Приём 28 — Замена механической схемы

> Заменить механическую схему на акустическую/оптическую/электрическую/... .

**Применение к OPA/PDP:**
Заменить Rego-интерпретатор (механически исполняет правила) на **neural policy engine** — small transformer, обученный на (context → decision) mappings. Latency < 0.5 ms, без компиляции.

Trade-off: explainability теряется, но latency ↓. Для критичных политик — fallback на Rego.

**Результат:** **Neural Policy Engine** (ADR-0028).

### 4.17. Приём 35 — Изменение физико-химических параметров

> Изменить концентрацию, консистенцию, температуру и т.п.

**Применение к сканеру как системе:**
Изменить «агрегатное состояние» сканера с **тяжёлого stateful сервиса** на **stateless function** + external state.

- Scanner = pure function `f(prompt, context) -> verdict`.
- State (cache, audit, policies) — external, durable.
- Scanner scales infinitely (no in-memory state).
- Deploy = serverless function (Lambda/Cloud Function).

**Результат:** **Serverless Scanner** (ADR-0029).

## 5. Законы развития технических систем

ТРИЗ формулирует законы эволюции систем. Применим к сканеру:

### 5.1. Закон полноты частей

Система работоспособна, если есть: **двигатель, трансмиссия, рабочий орган, орган управления**.

| Часть | В сканере |
|---|---|
| Двигатель (источник энергии) | LLM-провайдер (semantic engine) + rule engine |
| Трансмиссия (передача) | Pipeline orchestrator |
| Рабочий орган | Detectors + Redactor |
| Орган управления | PDP (OPA) + Feedback loop |

**Вывод:** система полна, но **двигатель** можно упростить — заменить отдельную ML-инфраструктуру на сам LLM-провайдер (LLM-as-judge). Это и есть ИКР.

### 5.2. Закон энергопроводности

Энергия должна свободно проходить через все части системы.

В сканере «энергия» = **информация (промпт)**. Должна свободно течь user → scanner → LLM → scanner → user. Текущая архитектура создаёт **бутылочные горлышки**:
- Vault roundtrip (для PII),
- OPA evaluation,
- ML inference.

**Улучшение:** pipeline должен быть **прямым** — каждый компонент работает с потоком, без roundtrip.

### 5.3. Закон согласования ритмов

Части системы должны работать в согласованном ритме.

- LLM стримит на ~50 токенов/сек.
- Streaming inspector должен работать на ~50 токенов/сек (chunk = 8 tokens, inspect = 160ms).
- Текущий inspect (5ms/chunk) — слишком быстрый, можно **увеличить granularность** до N=16 tokens (covering 320ms).
- ML classifier (slow path) — async, не синхронизирован со стримом, ОК.

**Вывод:** chunk size должен быть **синхронизирован** с LLM throughput, а не выбран произвольно.

### 5.4. Закон увеличения степени идеальности

Система эволюционирует в направлении: **функция ↑, ресурсы ↓**.

| Этап | Функция | Ресурсы (компоненты) | Идеальность |
|---|---|---|---|
| MVP | Базовая проверка | 14 компонентов | 0.07 |
| Phase 2 | Streaming, audit, redaction | 14 (без роста) | 0.14 |
| Phase 3 (ТРИЗ) | + Multi-tenancy, ML | 8 (после fusion) | 0.4 |
| Phase 4 (ИКР) | LLM-native safety | 0 (scanner исчезает) | ∞ |

### 5.5. Закон неравномерности развития

Части системы развиваются неравномерно → возникают противоречия.

Текущая архитектура: ML-классификатор развивается быстро (weekly retrain), а rule engine — статично. Это создаёт **дисбаланс**: ML опережает, rules устаревают.

**Улучшение:** Rule engine должен тоже **auto-evolve** — извлекать новые regex из blocked-by-ML-but-not-by-rules случаев. См. ADR-0025 (Adversarial Reinforcement Loop).

## 6. Вепольный анализ

Веполь = **вещество + поле**. Анализируем ключевые взаимодействия.

### 6.1. Веполь «Пользователь — Сканер — LLM»

```
         [Поле: TCP/HTTP]
              │
[Вещество: User] ─── [Вещество: Scanner] ─── [Вещество: LLM]
                          │
                  [Поле: ML inference]
                          │
                  [Вещество: Detector]
```

**Проблема:** Сканер является «веществом-посредником» — добавляет задержку. В ТРИЗ посредник убирается через слияние полей.

**Решение (ИКР-направление):** слить сканер с LLM — LLM сама становится сканером (через RLHF). Поле «ML inference» становится внутренним для LLM.

### 6.2. Веполь «Промпт — Embedding — Vector DB»

```
[Промпт] ─[поле: embedding model]─> [Vector] ─[поле: ANN search]─> [Vector DB] ─> [Similar attacks]
```

**Проблема:** длинная цепочка преобразований, каждое = задержка.

**Решение (ТРИЗ-приём 5 «Объединение»):** обучить embedding-модель сразу выдавать **класс угрозы** (multi-task). Тогда отдельный vector search не нужен для типичных случаев.

### 6.3. Веполь «PII — Vault — LLM»

```
[PII] ─[поле: redaction]─> [Token] ─[поле: network]─> [LLM] ─[поле: response]─> [Token] ─[поле: lookup]─> [PII]
```

**Проблема:** двойной roundtrip через Vault.

**Решение (ТРИЗ-приём 13 «Наоборот»):** не маскировать, а обучить LLM **не выводить PII** (RLHF). Vault остаётся только для audit tokenization (offline).

## 7. Ресурсный анализ

ТРИЗ требует найти **бесплатные ресурсы** в системе, которые не используются.

### 7.1. Ресурсы времени

| Ресурс | Где есть | Как использовать |
|---|---|---|
| Время ожидания LLM-ответа (3–15 сек) | LLM inference | Запускать deep analysis предыдущего промпта в параллель |
| Время между промптами пользователя | Сессия | Precompute вердикты для следующих вероятных промптов (predictive) |
| Время low-traffic hours (ночь) | Production | Batch retrain, audit hashchain verification, cache prewarming |

### 7.2. Ресурсы пространства (информации)

| Ресурс | Где есть | Как использовать |
|---|---|---|
| KV-cache LLM | LLM-провайдер | Semantic-представление промпта доступно без отдельного embedding |
| Tokenizer LLM | LLM-провайдер | Использовать для token-level redaction без своей tokenizer |
| System prompt | AI-приложение | Контекст для адаптивной политики |
| Metadata запроса (headers, IP, time) | HTTP-слой | Источник risk-сигналов без ML |

### 7.3. Ресурсы вещества (данных)

| Ресурс | Где есть | Как использовать |
|---|---|---|
| Логи LLM-провайдера | LLM API | Audit trail уже там — синхронизировать с нашим audit |
| Blocked промпты | Audit store | Бесплатный training corpus (ADR-0025) |
| FP/FN labels | SecOps | Continuous improvement (ADR-0013) |
| Public jailbreak corpus | Open source (AdvBench, JailbreakBench) | Bootstrap training corpus |

### 7.4. Ресурсы полей (внешние источники)

| Ресурс | Где есть | Как использовать |
|---|---|---|
| Семантическое поле LLM | LLM-провайдер | LLM-as-judge для edge cases |
| Compliance frameworks | OWASP, NIST | Безопасность по умолчанию |
| Academic research | Papers | Новые методы детекции |

## 8. Модель «Маленькие люди»

Представим компоненты как «маленьких людей» (агентов) с целями. Это помогает увидеть противоречия в поведении.

### 8.1. Сценарий: пользователь отправляет промпт

| Агент | Цель | Что мешает |
|---|---|---|
| 👤 Пользователь | Быстро получить ответ | Сканер задерживает |
| 🛡️ Сканер | Проверить безопасность | Не успевает за LLM |
| 🤖 LLM | Сгенерировать ответ | Сканер модифицирует ввод |
| 🔐 Vault | Хранить секреты | Слишком много roundtrip'ов |
| 📊 Auditor | Записать всё | Storage растёт |

**Противоречие:** Сканер хочет времени на проверку, пользователь хочет мгновенного ответа.

**ТРИЗ-решение:** Разделить «маленьких людей» во времени — сканер проверяет **пока LLM генерирует**, а не до. (Приём 10 «Предварительное действие».)

### 8.2. Сценарий: LLM сгенерировала вредоносный ответ

| Агент | Цель | Что мешает |
|---|---|---|
| 🤖 LLM | Выдать ответ | Сканер блокирует |
| 👤 Пользователь | Получить ответ | Сканер обрывает stream |
| 🛡️ Сканер | Не допустить утечку | Поздно — уже стримит |
| 📊 Auditor | Зафиксировать инцидент | Не успевает real-time |

**ТРИЗ-решение:** Буфер-«страж» перед пользователем — принимает чанки от LLM, но отдаёт пользователю с задержкой в 1 чанк (на проверку). (Приём 11 «Заранее подложенная подушка».)

## 11. Критика самой ТРИЗ-аппликации

Чтобы быть честным, отметим ограничения применения ТРИЗ к данной архитектуре:

1. **ТРИЗ создана для физических систем** — некоторые приёмы (17, 28) интерпретируются метафорически, не буквально. Риск «натянуть сову на глобус».
2. **40 приёмов — эвристика, не гарантия** — конкретное решение может быть плохо для нашего контекста (например, ADR-0023 LLM-native PII через RLHF — требует $100K+ дообучения LLM, что недоступно команде).
3. **ИКР «сканер исчезает» — маркетинговая иллюзия**. На практике всё равно нужен кто-то, кто выполняет функцию. ИКР — направление, не конечная точка.
4. **Много решений на бумаге, мало в production** — ADR-0017..0029 это **гипотезы**, требующие empirical validation.
5. **ТРИЗ не учитывает бизнес-контекст** — что стоит денег, что доступно команде. Например, ADR-0028 (Neural Policy Engine) — технически интересно, но потеря explainability критична для compliance.

**Принцип применения:** ТРИЗ-решения — это **кандидаты для экспериментов**, не direct-to-prod решения. Каждое требует PoC + метрик.

## 12. Резюме

Применение ТРИЗ к архитектуре LLM Security Scanner дало:

- **12 технических противоречий** явно сформулированы (раздел 3.1).
- **3 физических противоречия** (раздел 3.2) — самая важная находка: они не решаемы компромиссом, требуют ТРИЗ-приёмов.
- **17 приёмов** применены, породив **14 новых ADR** (ADR-0016..0029).
- **5 законов развития** объясняют, почему текущая архитектура будет эволюционировать к слиянию сканера с LLM-инфраструктурой.
- **ИКР** задан как направление: **сканер исчезает, функция остаётся**.

Главный сдвиг парадигмы: не «достроить сканер», а «**сделать безопасность свойством LLM-инфраструктуры**». Это меняет product roadmap и competitive positioning.
